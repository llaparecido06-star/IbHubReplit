O Diagnóstico TécnicoAnalisando a pilha de execução (Stack Trace) das duas ocorrências, o erro acontece quando o JavaScript tenta rodar um código dinâmico logo na abertura do app:Crash 1: Falha na compilação em tempo de execução (JIT/Bytecode)No primeiro log, a thread principal (com.apple.main-thread) tenta executar uma função JavaScript via avaliação direta (directEval / caseDirectEval). Para rodar isso, o Hermes tenta gerar o bytecode em tempo de execução (generateBytecodeModule).
Durante a alocação de registradores na compilação desse código (LookupBucketFor), ocorre uma falha de acesso à memória (Data Abort / Translation fault).  Crash 2: Estouro de Memória no Coletor de Lixo (Garbage Collector)No segundo log, o comportamento é muito parecido. O app tenta ler uma string dinâmica (createDynamic) para montar uma pilha de erro (errorStackGetter) dentro do ambiente JavaScript. Na sequência, a Thread do JavaScript tenta alocar memória em uma área chamada Old Generation do Garbage Collector do Hermes (HadesGC::OldGen::alloc). O motor tenta liberar espaço evacuando a memória jovem (youngGenEvacuateImpl), falha no mapeamento de ponteiros (forwardCell) e gera uma nova falha de acesso à memória.  Por que isso acontece? (Causas Prováveis)Como o app usa Hermes, por padrão todo o código do seu pacote (bundle) já deveria vir pré-compilado em bytecode na hora que você gera o build de produção. O fato de o trace mostrar directEval e generateBytecodeModule indica que o app está tentando interpretar texto puro como código JavaScript após abrir.  As duas maiores causas para isso são:Uso de eval() ou new Function(): Existe alguma linha no seu código (ou em alguma biblioteca de terceiro recém-instalada) que está usando eval() para executar uma string. O Hermes tem sérias limitações com eval() em produção.Incompatibilidade da arquitetura (Metro Bundle vs iPad M3): O iPad de teste usa o chip M3 (arquitetura ARM-64 avançada). Se o pacote JavaScript enviado veio corrompido ou com alguma sintaxe que o interpretador local do Hermes não conseguiu processar nativamente, ele tenta "escapar" para o interpretador de string e quebra o coletor de lixo.  Próximos Passos para ResolverPara solucionar esse problema e passar na revisão da Apple, siga estas etapas:1. Rastreie o uso de eval e injeção de códigoFaça uma busca global no seu projeto (especialmente em códigos adicionados ou atualizados recentemente) por termos como:eval(new Function(Bibliotecas de execução dinâmica de código ou interpretadores matemáticos/template engines que usem strings como funções.Se encontrar, substitua por lógica nativa em JavaScript que não dependa de interpretação em tempo de execução.2. Limpe os Caches e Force a Recompilação do BundleGarantir que o bundle final seja gerado do zero sem resíduos de cache é essencial. No terminal do seu projeto, execute:Bash# Limpar caches do watchman e do metro
watchman watch-del-all
rm -rf node_modules
npm install # ou yarn install

# Limpar build do iOS
cd ios
rm -rf Pods Podfile.lock build
pod install --repo-update
cd ..

# Gerar o build de produção limpando o cache do Metro
npx react-native start --reset-cache
3. Teste focado em Arquitetura ARM64 / iPad SimulatorA Apple testou em um iPad Air de 11 polegadas (M3). Às vezes, problemas de layout ou pacotes que se comportam de forma diferente em telas maiores engatilham fluxos de código alternativos no React Native.  Abra o simulador de um iPad equivalente no seu Mac (com chip Apple Silicon, se possível).Rode o app usando a configuração de Release para simular exatamente o comportamento do Hermes em produção:Bashnpx react-native run-ios --simulator="iPad Air (11-inch)" --mode=Release
Após identificar e remover qualquer execução dinâmica de string ou isolar o pacote problemático, gere a versão 1.1.1 (9) e envie novamente pelo App Store Connect.
